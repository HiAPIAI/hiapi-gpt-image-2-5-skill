# Upgrade policy

The runtime checks the central directory first and repository policy second. Below `minimumVersion` blocks new paid creation; below `latestVersion` emits a notice and continues. If update sources are unavailable, the version is unverified but local validation still permits new creation; recovery and non-billing preflight remain usable. An update-service outage does not become a generation outage.

Version 0.4.0 is a soft upgrade: `latestVersion` is `0.4.0` and `minimumVersion` stays `0.3.1`. Production changed the `@pro` contract — `aspect_ratio` became a 15-ratio-plus-`WxH` pattern with no `auto`, `quality` lost `auto` and now defaults to `medium`, `resolution` became a real `@pro` input, `framing` appeared as a server-computed billing tier, and pricing became fixed rules over `{framing, quality, resolution}`. Copies older than 0.4.0 still create valid tasks whenever they send the schema defaults (`1:1`, `medium`, no `resolution`), because those fall in the schema-default cell; their only defects are rejecting the new `--resolution` flag, accepting `quality=auto` / `aspect_ratio=auto` locally (which production now rejects), and failing to match the three-key price rules in `--estimate`. The mode route is unchanged, so forcing every installed copy to update would block valid work it still handles correctly. Publishing 0.4.0 raises the notice and leaves 0.3.1 usable. Raising `minimumVersion` to 0.4.0 is a later decision once 0.4.0 has spread. The central `hiapi-skills` entry and this repository policy must agree; a successful central lookup takes precedence over the repository fallback. Preflight and recovery remain available to older copies.

Version 0.3.2 was a soft upgrade: `latestVersion` `0.3.2` with `minimumVersion` held at `0.3.1`, because 0.3.1 still sends valid requests and only over-restricts prompt length locally.
